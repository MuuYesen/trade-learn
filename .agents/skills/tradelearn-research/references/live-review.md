# 实盘复盘

目的：把实盘里实际发生的事和回测时的假设对照，找出偏差，再回到研究里改进。策略上线后，问题从"有没有收益"变成"还有没有"。

## 一、上线之前：写好停用条件

在**第一笔模拟盘或实盘交易之前**，和第 1 步的证伪条件一起写下停用条件，存进实验记录。回撤开始之后再定，每一次偏离都能找到解释。可用的一组：

- **回撤**：超过模拟回撤分布的 95% 分位（不是历史最大回撤）。
- **时长**：水下时间超过模拟分布中恢复时间的 95% 分位。
- **偏离**：在足够长的窗口里，实盘夏普低于样本外估计两个标准误以上。
- **机制**：策略赚钱的结构性原因已经改变——交易所改了费率、对手方离场、规则变了。这一条立即生效，不等统计结果。

前三条是统计性的、慢的；第四条最能及时止损，而它要求知道策略为什么赚钱，所以第 1 步必须写下机制。触发后怎么处理由用户决定。

## 二、实盘样本很小

半年实盘看起来比十年回测"更真实"，于是被两个方向过度解读。按标准误公式，真实年化夏普 0.8 的策略，半年实盘的标准误约 1.6：实盘夏普在 −2.4 到 4.0 之间都与"策略按设计运行"一致。

- 开局好**不是**确认，不是加仓的理由。
- 开局差**不是**证伪，除非触发了事先写好的停用条件。

**只能在跑实盘的那台机器上做。** 如果你在 Muse 这类云电脑上，告诉用户复盘要在他的实盘服务器上进行，不要让用户把凭据交给你。

## 三、取实盘数据

按顺序选择第一种可用的方式。

### 方式 A：Sentinel 只读查询（推荐）

条件：能 `from tradelearn import sentinel`，环境变量里有 `LEAFQUANT_ENDPOINT`，并且用户已开通只读查询。

```python
from tradelearn import sentinel

c = sentinel.connect()          # 读取环境变量里的接入地址和凭据，不需要你接触凭据本身
c.strategies()                  # 用户名下的策略
c.describe()                    # 有哪些表、字段、指标、日志类型，各自的含义和口径——先看这个再写查询
c.sql("SELECT …")               # Sentinel 与复盘的业务结果
c.metrics("…", start, end, step)  # 运行时序（看板背后的数据）
c.logs("…", start, end, limit)  # 日志原文
```

- 先 `describe()`，按它给出的表名和字段写查询，不要猜。
- 查询只读，只能看到这个用户自己的数据。
- 返回结果附带口径和数据截止时间；复盘结论里的数字**以这些口径为准**，你自己算的只用来核对。
- 报"未开通"时，告诉用户可以开通，并改用方式 B。
- 已安装的 TradeLearn 里还没有 `tradelearn.sentinel`，或者调用报接口不存在时，说明这个版本尚未提供只读查询，直接改用方式 B 或 C，不要自己拼接口地址去请求。

### 方式 B：本机的实盘日志

策略运行时会把日志先写在本机的状态目录里：`<state_dir>/segments/*.log`。

- 每行一条 JSON 记录；**只用以换行结尾的完整行**，最后一行如果没有换行，说明写入被中断，忽略它。
- 每条记录带策略、账户、来源和字段，字段需要用 TradeLearn 自带的解码函数还原（当前版本为 `leafquant_monitor.codec.decode_fact`；名称随版本可能调整，以已安装包为准）。
- 常见的记录类型：信号（`SIGNAL_START`）、风控检查（`RISK_CHECK`）、下单（`ORDER_SEND`）、交易所确认（`EXCHANGE_ACK`）、成交（`ORDER_FILL`）、行情观测（`BAR_OBSERVATION`）、心跳（`HEARTBEAT`）。
- 只读，不要改动或移动这些文件——它们是发往 Sentinel 的原件。

### 方式 C：用户下载的原文

用户可以在 Sentinel 的「日志」页面下载原始文件交给你，格式和方式 B 相同。

## 四、对照什么

| 项目 | 怎么看 | 说明什么 |
|---|---|---|
| **成交价偏差** | 实际成交价 vs 回测在同一时点假设的成交价 | 回测的滑点假设是否太乐观 |
| **成交率** | 发出的订单中实际成交的比例 | 回测是否默认了"全部成交" |
| **执行耗时** | 从信号到下单、到确认、到成交的时间 | 信号是否因为延迟而失效 |
| **信号衰减** | 同一信号在回测里和实盘里的收益 | 是否存在实盘拿不到的那部分收益 |
| **成本** | 实际手续费、资金费 vs 回测设置 | 成本假设是否偏低 |
| **漏单与多单** | 回测有、实盘没有的交易，以及反过来 | 实盘与回测逻辑是否一致 |

**和分布比，不和单条曲线比。** 回测是一个点；第 5 步的蒙特卡洛分布才是参照。实盘落在分布的第 30 个百分位很正常，跌到第 5 个以下才是信号。

**成本偏差和信号偏差分开算。** 实盘跑输最常见的原因不是收益消失，而是滑点和费用高于假设。两者的处理不同：前者是执行问题，后者是策略问题。先把实际成本代回回测，剩下的差距才归到信号上。

**把执行成本拆开**（执行缺口分解）。相对于**决策时的价格**，每笔多付的部分拆成：
- **择时**：从决策价到执行基准（到达价、VWAP 或 TWAP）的漂移；
- **冲击**：自身订单推动价格，常用平方根模型估计 `k × 波动率 × sqrt(成交量 / 日均成交量)`；
- **点差**：有买卖报价时直接算，没有时用高低价近似并写明；
- **费用**：佣金、税费；
- **滑点**：成交价相对所选基准的剩余部分。
按标的、方向、日期汇总，找出成本主要来自哪一项和哪些异常大单。

**用实际成交校准回测成本**。参考价只能取成交**当时或之前**的报价或 bar，不能用之后的价格；有报价时用中间价和点差，只有 bar 时用上一根收盘价并说明。带符号的滑点（价格改善为负）和成本绝对值分开报告。按参与率分组得到成本曲线，**只在观测到的参与率范围内使用**，外推要作为敏感性假设单独说明。

**容量**：成交量占日均成交量超过约 20% 已属激进，超过 100% 不现实。把资金规模放大到 0.25、0.5、1、2、4、8 倍估计冲击成本，找出收益被冲击吃光的规模。

有 Sentinel 的执行复盘数据时，**Markout**（成交后 10 秒到 300 秒，成交价相对之后中间价的变化）直接说明了下单时机的好坏：长期为负，说明总是在对自己不利的价格上成交。

## 五、判断原因

把近期窗口和等长的历史窗口（或样本外窗口）对比：收益、波动、夏普、胜率、回撤、换手；有因子 IC、基准、行情标签时一并比较。然后把差距归到四类原因上：

| 原因 | 典型迹象 |
|---|---|
| **信号** | IC 下降、分组不再单调、同类信号普遍失效 |
| **行情** | 只在某类行情下变差，换回相近行情后恢复 |
| **数据** | 实盘数据源、时区、字段与回测不同；缺失或延迟 |
| **执行** | 成本、成交率、延迟偏离假设；信号本身没变 |

报告时把**事实、诊断迹象、待验证的假设、数据限制**分开写，并写明窗口和样本量。

**停用与恢复的规则也要能回测。** 降权、暂停、恢复的判断只能用当时已经可得的数据；同时算出"如果一直不停"的对照，报告停用的机会成本。不要事后根据收益挑停用的月份。

## 六、用 Sentinel 复盘：先读现成结果

Sentinel 已经把实盘数据算成了复盘结果。**先读这些结果，以它们为准**；不要从原始日志另算一套再和它比谁对。原始日志用来逐笔核对、查疑点。

| Sentinel 里有的 | 回答什么问题 | 怎么用 |
|---|---|---|
| **执行复盘**：每笔成交后 10 到 300 秒各期限的 Markout 分布 | 下单时机好不好 | 各期限的中位数长期为负，说明总在对自己不利的价格成交（被人"抢先"或追涨杀跌）；只在短期限为负、长期限转正，多半是冲击成本而不是方向错了 |
| **三项延迟**：决策、交易所确认、成交，都从同一次下单起计 | 慢在哪一段 | 和回测假设的成交时点比；延迟长的那部分订单单独看 Markout，判断延迟是否吃掉了信号 |
| **指数增强复盘**：账户对基准的走势和收益归因 | 超额来自哪里 | 归因到配置、选股、费用等；跟踪误差突然变大先查持仓与目标是否一致 |
| **看板时序**：权益、持仓、成交、运行状态 | 整体表现与运行是否正常 | 把实盘权益放到回测的模拟分布里看落在哪个分位；先排除断线、停机、拒单这类运行问题 |
| **原始日志**：信号、风控、下单、确认、成交、行情观测 | 每一笔到底发生了什么 | 和回测在同一时点的信号与成交逐笔对齐，找漏单、多单和价格偏差 |

查询前先用 `c.describe()` 看这些结果在哪张表、哪个指标、字段是什么含义，再写查询。

## 七、按策略类型看重点

| 策略类型 | 先看 | 再看 |
|---|---|---|
| **高频、做市、日内** | 执行复盘的 Markout、三项延迟、成交率与撤单 | 成本拆分（择时、冲击、点差、费用）、库存与持仓时间 |
| **趋势、CTA、时序择时** | 信号与成交时点的偏差、滑点、漏单 | 持仓期收益与回测同一笔的对比、行情分段表现 |
| **指数增强、截面选股** | 对基准的超额与跟踪误差、收益归因 | 实际持仓与目标持仓的差、调仓成本、因子暴露漂移 |

## 八、用户一句话发起复盘时

例如"复盘一下这周的实盘，和回测比滑点差多少"。按这个顺序做，不要先问细节：

1. `c.strategies()` 找到对应策略；用户有多个策略又没说清时，列出来让用户选。
2. 定窗口：用户说的区间；没说就取最近一周，并写明。同时确认窗口内**策略版本**有没有变——跨版本的数据要分开看。
3. 先看运行是否正常：看板时序里的断线、停机、拒单。运行有问题，先报告运行问题，再谈策略。
4. 读现成复盘结果：按第七节的策略类型取对应的执行复盘或指数增强复盘。
5. 用同一窗口、同一参数在 TradeLearn 里重跑回测，逐项对照第四节的表；用户问的那一项（例如滑点）放在最前面。
6. 用第五节的四类原因下判断，按 `report.md` 的实盘复盘部分写报告。

## 九、从复盘到优化

1. **把实测值代回回测**：用 Sentinel 实测的滑点、延迟、成交率替换原来的假设（例如滑点改成实测中位数，延迟按实测分布推后成交），先重跑**原策略**——这一步回答"按真实执行条件，原策略本来应该是什么表现"。
2. **再提改进**：一次只改一个主要因素，写清"看到的偏差 → 可能原因 → 改什么 → 预期哪个指标变好 → 可能的代价 → 什么结果说明改错了"。
3. **按完整研究流程验证**：改动要过 SKILL.md 的第 3–6 步，用原策略没参与过选择的时间段检验；不能用这次复盘发现问题的那段数据来证明改好了。
4. **交给用户决定**：给出改动方案、验证结果和风险。**要不要上线、什么时候上线，由用户决定**；改动实盘的任何东西都要用户逐次确认。
5. **上线后对比前后**：新版本上线后，在 Sentinel 里按**版本和时间段**分开取数，对比改动前后的同一指标（例如 Markout 中位数、滑点、成交率）。窗口要够长，用第二节的标准误判断差异是不是噪声；不要上线几天就下结论。
6. **记录**：把复盘结论、修正后的假设、改动和前后对比一起记进实验记录，下次复盘直接对照。
